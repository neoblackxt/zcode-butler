## 三桥是什么

整段代码包在一个守卫里:`if (window.chrome && window.chrome.webview)`——**只有被 WebView2 宿主加载时才激活，普通浏览器里整段休眠**。它们是“网页”变成“桌面悬浮窗公民”的适配层：

1. **数据桥**(470–477 行)：监听宿主发来的 `{"type":"data",payload}`,把 `account.fiveHour.pct / weekly / mcpMonthly / keys` 映射到四个环；页面加载完发 `{"type":"ready"}` 告诉宿主“可以推数据了”。浏览器里没有 `chrome.webview`,所以环上永远是写死的演示值——这就是回落机制。
2. **拖动桥**(480–484 行):WebView 会吃掉鼠标事件，WPF 窗口自己收不到拖动；所以面板区 `pointerdown` → `postMessage('drag')` → 宿主执行 DragMove。`.fab-zone` 除外，因为齿轮按钮有自己的悬停/点击交互。
3. **形状上报**(487–539 行)：布局落定后，用 `getPointAtLength` 沿**实际渲染出来的**面板路径每 4 舞台像素重采样，连同弧形按钮的带状区域、fab 圆心半径、devicePixelRatio,打包成 `{"type":"shape",...}` 发给宿主——宿主拿这些点建 WM_NCHITTEST 命中掩码，实现“面板内可点、月牙空隙穿透”。合成宿主下渲染与命中是分离的，这份上报就是命中的唯一依据。

## 原型自带三桥？可以，而且是理想情况——但有个隐蔽前提

**浏览器预览完全不受影响**：因为整段桥代码在 `chrome.webview` 不存在时自动休眠，带桥的原型在浏览器里的表现和不带桥一模一样。合入时也省事——SOP 的“阶段二：接入三桥”直接坍缩成零工作量，合并就是纯视觉替换。

**但隐蔽前提是：桥里硬编码了一批几何锚点，原型改了几何，桥就悄悄失效。** 看代码就明白，形状上报假设了一堆常量：

- 元素锚点:`#panelPath`、`.stage`、`#arcPath`、`.fab-zone` 这些 id/class 必须还在；
- 舞台常量:`430×2025`、fab SVG 左上角偏移 `(220.5, 1578)`、fab 圆心 `(317, 1675)`、半径 84、弧线描边 22.3;
- 数据桥的目标:四个环的 id(`5h/7d/mcp/key`)。

**失效方式特别阴险**：桥在浏览器里休眠，所以锚点对不上的问题**在浏览器预览中完全不可见**，只有到真机上才表现为——点击穿透区域错位、面板拖不动、或掩码贴不紧曲线边缘。而真机又没有 DevTools,排查起来最贵。

所以分两种情况：

- **你的“原型”其实是正本的复制品**(从 `butler-widget.html` 复制出来迭代)：桥跟着文件一起带着，锚点和几何天然同步，这是最好的路径，合入零风险；
- **原型是 OpenDesign 从头生成的**(比如桌面那份 `ai-sidebar-widget.html`——卡片式居中布局、白底、无桥)：它“自带三桥”就得有人手工把桥贴进去并**重新量测所有锚点常量**，因为新设计的 fab 位置、舞台尺寸大概率变了。SOP 阶段二存在的意义就是这个。

一个值得做的改进：如果以后想固定走“原型自带桥”的流程，可以把桥里的硬编码锚点改成运行时实测(比如 fab 圆心从 `#arcPath` 的 `getBoundingClientRect` 算，而不是写死 317/1675)。桥变成几何无关之后，OpenDesign 随便怎么改设计，桥都不用动——那才是真正消掉阶段二。需要的话我可以帮你改。



## 三桥的改动一般是在ZCode合入项目UI源码的阶段是吧

对，确认无误——桥的改动永远发生在**合入接线阶段**，由 zcode 在正本里完成，不发生在 OpenDesign 设计阶段，也基本不发生在壳(ps1)阶段。精确地说，触发桥改动的是**结构变化**，不是视觉变化：

- **纯视觉改动**(换色、调间距、改动画、改字体)：桥一个字都不用动，正本直接改；
- **结构变化**(合入新原型、新增面板/可点区域、fab 或舞台挪位、环增减)：桥要动——新形状进 shape 上报、新交互区加拖动排除、锚点常量重新量。而“合入新原型”和“拓展新 UI”这两个动作本身就是合入阶段的事，所以桥的改动天然集中在那里。

另外一个补充：桥严格说是**一对**——页面侧(html 里的上报代码)+ 宿主侧(ps1 里收 `drag`/`shape`/`ready`/`data` 消息的处理)。合入阶段 zcode 改的是页面侧；宿主侧只在**消息协议本身**变了时才动(比如以后新增一种消息类型)，那属于壳层改动，按 SOP 要先做 DLL-Runtime 配对检查那套流程。目前协议稳定，宿主侧基本是零改动的。



## “三桥”和“一对”不矛盾，是两个维度

**“三”按功能数，“一对”按位置数。** 三条通道，每条通道都有两端——就像三座桥，每座桥都有两个桥头：

| 桥(功能) | 页面侧桥头(html 里的 JS)           | 宿主侧桥头(ps1 里的处理)                  |
| :------- | :--------------------------------- | :---------------------------------------- |
| 数据桥   | 470–477 行：发 `ready`、收 `data`  | 收到 `ready` 后把 status.mjs 的数据推进来 |
| 拖动桥   | 480–484 行:`pointerdown` 发 `drag` | 收到 `drag` 执行 DragMove()               |
| 形状上报 | 487–539 行：量形状发 `shape`       | 收到 `shape` 建 NCHITTEST 点击掩码        |

平时说的“三桥”指页面侧这三段代码；上次说“严格是一对”是想提醒你：**每段代码都有个 ps1 里的对端**，合入阶段 zcode 改的是页面侧这一头，宿主侧那一头只在消息协议本身变的时候才动。两句话说的是同一套东西的不同切面。



## 不是说,桥属于代码活,zcode管吗,到那时带桥正本就可以整个丢给 OpenDesign 或任何工具改视觉，改完原样跑，不再需要剥桥、不再需要重新量测合入吗

不矛盾——那两句话说的是**改造前和改造后两个世界**，而且你这一问正好逼我把上次那句话说得更严谨。核心在于：桥需要被保护的东西，改造前后不一样。

#### **改造前，桥有两个脆弱点**

1. **几何耦合**：桥里写死了 317/1675/84/22.3 这些设计坐标。谁动了 fab 的位置或尺寸，桥就静默错位。所以每次结构改动，必须有个懂宿主协议的人重新量、重新填——这就是“合入是代码活、zcode 管”的真正含义。
2. **代码易碎**：桥那 70 行 JS 对重新生成式的工具来说就是异物，OpenDesign 整文件重生成时会把它丢掉或改坏。所以要“剥桥给设计基线”。

#### **改造后，第 1 个脆弱点消失，第 2 个还在**

把锚点改成运行时实测后：

- **“改视觉”和“动桥”彻底解耦**——挪位置、改尺寸、加粗描边，桥自己量自己适应，**任何人都不用再碰桥**。注意这不等于“桥归 OpenDesign 管了”：桥仍然是 zcode 的代码，只是“日常改视觉”这件事不再需要 zcode 介入量测。所有权没变，工作量消失了。
- **但重新生成式工具丢 script 块的问题，改造解决不了。** 这是我上次那句“丢给任何工具”说过头的地方，现在修正：它成立的前提是该工具做**就地编辑**(像 AI 代码编辑器那样在原文件上改，保留 script 块)。而 OpenDesign 看起来是整文件重新生成的——对它，合入这道工序还在，只是从“贴桥 + 重新量锚点”退化成“把桥块原样粘贴回去”，纯机械操作，30 秒，不需要任何量测。

#### **一张表说清**

| 你做的事              | 改造前                            | 改造后                                           |
| --------------------- | --------------------------------- | ------------------------------------------------ |
| 改颜色/间距/动画      | 直接改正本                        | 一样(从来不用动桥)                               |
| 挪 fab / 改尺寸       | zcode 重新量锚点填常量            | **桥自动适应，没人需要动它**                     |
| OpenDesign 重生成视觉 | 剥桥基线 + 合入时贴桥 + 重新量测  | 贴桥块即可(免量测)；若工具能就地编辑则连这步都免 |
| 新增交互面板/按钮     | zcode 改桥(shape 覆盖 + 拖动排除) | **一样——这是真正的代码活，改造不豁免**           |

最后一行是关键：改造消除的是“**桥跟着几何跑**”的维护成本，不消除“**桥跟着交互结构长**”的开发工作。新面板要进掩码、新按钮要逃出拖动区，这永远需要懂协议的人写代码——那部分始终是 zcode 的活，跟你最初理解的“桥属于代码活”完全一致。

**第三层(最次要)：每次对话里的临时提示词。** 改造落地后，你给 zcode 的合入指令可以短到一句话：“把 docs/ui/xx.html 合入正本，按 SOP 验收”。因为规则已经被下面两层接住了。

**第二层：给 OpenDesign 的提示词模板**(它的输出里没有桥，所以只约束结构契约)：

> 基于 docs/ui/设计基线.html 迭代视觉。硬约束：① 自包含单文件，无外链 JS/CSS/字体/图片；② 保留元素锚点:`.stage`、`#panelPath`、`#arcPath`、`.fab-zone`、四环 ID(`5h/7d/mcp/key`);③ 舞台 430×2025、面板贴右缘、左外侧为透明区，新元素画在面板带内；④ 数据静态演示值写死。

**第一层(最重要)：写进 AGENTS.md 的持久提示词。** AGENTS.md 是每个 zcode 会话自动加载的——规则写在这里，你就永远不用在对话里重复。在“AI 协作红线”下加一节，文本给你拟好了：

> **三桥铁律(butler-widget.html)**
> - 形状上报桥只准运行时实测(`getBoundingClientRect` / `getComputedStyle` / `getPointAtLength`),**禁止写入任何设计坐标常量**(圆心、半径、描边宽、元素舞台偏移)。发现硬编码一律视为 bug,改回实测。
> - 合入新视觉时，桥代码块(`chrome.webview` 守卫段)原样保留，不因几何变化改动；只有新增交互面时才扩桥——新可见形状加入 shape 采样，新可交互区加入拖动排除。
> - 合入验收必须对比 `%TEMP%\butler-widget-debug.log` 的 `mask pts` 数与改前一致(同 UI 结构下)。

## 为什么 mask pts 是关键验收信号

“桥还是自动的”这句话没法直接验证，但它有个客观代理指标：真机日志里的 `mask pts=N`(掩码点数)。合入前后各截一次日志，**同样结构下点数应该一致**——一致说明桥把新几何采样对了；对不上说明有人把实测改回了写死、或新形状没进采样。这比“看起来没问题”硬得多，也是唯一能让 AI 自己闭环验证的信号。
