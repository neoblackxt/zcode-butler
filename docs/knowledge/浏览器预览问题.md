### 1.原型合入项目源码之前的浏览器预览

1. **原型迭代期(合入前)**——大改版时，OpenDesign 产出的原型 html 本身就是自包含、带演示数据的，直接 `http.server` 起来在浏览器里打磨布局、动画、文字。这一轮确实发生在合入正本之前，你的直觉完全正确。
2. **正本验收期(合入后)**——SOP 阶段一预览的是**正本文件本身**(`plugins/.../widget/butler-widget.html`),这轮检查的不是设计，而是**合入这个动作没搞坏东西**：三桥还在不在、演示数据回落正常没、自包含没破、widget 模式的贴右 fit() 对不对。原型里没有桥、没有透明背景逻辑，这些只在合入后才存在——**变量隔离要隔离的“你的代码”，恰恰是‘正本+桥’这份最终要运行的字节**，它只在合入后才成形。



### 2.如果我在OpenDesign阶段就确认了原型(带桥或者不带桥)的效果,是不是就不用浏览器预览了

可以，但只在一半场景下成立——关键在于：**浏览器预览的价值从来不是“看效果”，而是三件 OpenDesign 预览环境做不到的事**。逐个对一下：

**1. 悬浮窗比例下的表现。** OpenDesign 的画布是按设计稿尺寸(430×2025)或自适应展示的，而真机是约 112×1050 物理像素、scale≈0.3 的窄条。0.3 倍下文字还清不清楚、44px 的百分比缩完是否可读、悬停判定区在这个尺度好不好命中——这些只在窄窗(220×810)里才能验。你在 OpenDesign 确认的“效果好”是大尺寸下的效果。

**2. Console 和 Network 检查。** 自包含契约(无外链 JS/CSS/字体/图片)在 OpenDesign 预览里看不见——预览环境宽松，外链字体照样渲染；但宿主是“单文件复制到 %TEMP% 再加载”，任何外链到了真机直接断链白屏。控制台报错同理(fit() 或齿轮生成代码一抛异常整页停摆)。这两个只能 DevTools 看。

**3. 合入后的那份，不等于你确认的那份。** 这是最本质的一条，直接按你问的两种情况分：

- **原型不带桥(fresh 生成，比如桌面上那份卡片式原型)**：合入时文件被改了——fit 从“居中 min 缩放”换成“贴右按高缩放”、背景换透明、三桥贴进去。**你在 OpenDesign 确认的是改造前的文件**，改造后长什么样你还没看过。浏览器预览正是合入后的第一次、也是最便宜的一次全量检查(视觉+桥完整+演示数据回落)，这步不能省。
- **原型带桥(正本的复制品，只动视觉)**：合入就是原样覆盖，字节没变，你确认的效果 = 将要运行的字节。这种情况下，**浏览器预览确实可以跳过，直接真机**。剩余风险只有上面 1、2 两点(窄窗尺度、自包含)，对“只改了个颜色/间距”级别的小改动风险趋近于零。

**但有个经济账要算清**：跳过浏览器预览省的是 1 分钟，而它兜住的问题一旦漏到真机——没有 DevTools、只有日志和截图、kill+start 一轮 15 秒起步、悬停验证还要跟真实鼠标竞态——一个自包含违规或 JS 报错的排查成本是分钟级的十倍。所以我的建议不是“能不能省”，而是把它**从必经阶段降级为抽查**：带桥原型的小改直接真机；大改、fresh 原型合入后、或改了任何带 `src/href/url()` 的东西，花 1 分钟开一次窄窗预览再上真机。省下的是流程，不是保险。





### 为什么要浏览器预览,,都合入项目源码了,为什么不直接看效果

问得对——真机当然能直接看，浏览器预览不是“必须”，它是**快速内循环**。我先确认一下你的宿主到底能不能在真机上开 DevTools,这决定答案的成色。

可以直说：真机当然能看、最终也必须看——浏览器预览不是替代验收，是**迭代期的快循环**。而你这个问题我去验证了一下，你的宿主恰好把真机调试的能力降到了最低，浏览器预览的价值因此更实：

**1. 真机上你没有任何检视工具(刚验证)。** 你的 `butler-widget.ps1` 没有启用 DevTools——grep 不到 `OpenDevTools` / `AreDevToolsEnabled`,宿主唯一的输出通道是 `%TEMP%\butler-widget-debug.log` 的纯文本日志和截图脚本。也就是说：真机上发现“这个环偏了 3px”,你没法看 DOM、没法在 Elements 里实时改 CSS 试、没法看 Console 报错，只能：猜 → 改文件 → kill+start 等 15 秒冷启动 → 截图 → 再猜。浏览器里这一轮是：F5(1 秒)→ DevTools 里直接拖数值看效果 → 满意了写回文件。一次样式打磨几十轮刷新，两种循环的差距是分钟级和小时级的区别。

还有个这个页面特有的原因：面板轮廓 path、齿轮 path、scale 都是 JS 运行时生成的——**磁盘源码里根本看不到渲染结果**，DevTools 的活 DOM 是唯一能检视“渲染后长什么样”的地方，而真机上没有 DevTools。

**2. 变量隔离：分清“我的代码错了”还是“壳错了”。** 真机效果 = 你的视觉代码 × 一堆宿主层：WebView2 透明合成、1.75 DPI 缩放、NCHITTEST 形状掩码、点击穿透、数据桥注入。真机上看着不对，你不知道该改 html 还是该查壳(你们复盘里的 DLL-Runtime 不配对就是壳层事故)。浏览器里只有纯视觉层——**在浏览器里就错的，一定是UI代码问题；浏览器里对、真机上错的，一定是壳或桥**。这个二分法正是 SOP 分阶段验收的意义，直接跳真机就失去了定位能力。

**3. 交互测试成本。** 真机悬停验证和真实鼠标竞态，你们的 SOP 自己写了“失败重试 3–5 次”；浏览器里悬停就是正常鼠标操作。另外 Network 面板能顺手检查自包含契约(无外链)，省得带着外链资源进宿主后栽在“临时副本单文件复制”机制上。

**什么时候可以跳过浏览器直接看真机**：改一个颜色 token、动一行文字这种确定性小改，kill+start 一步到位完全合理。浏览器预览挣的是“视觉打磨阶段”的钱——那个阶段你需要的是快速刷新和实时检视，这两样真机都给不了。



### 也就是两次浏览器检查,我除了看动画效果,还看什么

两次检查的重点不一样：合入前那次是给设计看的，合入后那次是给契约看的。动画其实只占很小一块，真正值钱的检查大多“看不见”——要用 DevTools 才能验。

#### 第一次：原型期(合入前，浏览器里打磨设计)

这次看的就是眼睛看的东西：布局比例、间距节奏、配色，加上交互态——悬停时弧线收进气泡的过渡顺不顺、齿轮点击转半圈的反馈、`Tab` 键盘聚焦时焦点圈位置对不对。这次基本可以不碰 DevTools。

#### 第二次：正本期(合入后，1–2 分钟过完这份清单)

按价值排序，前四条都是“肉眼看不见、漏了就真机事故”的：

1. **Console 零报错**(DevTools Console)。这个页面的 fit 缩放、齿轮 path、弧线全是 JS 生成的，任何一处抛异常整个 `<script>` 停摆，页面冻结在静态状态——而且看起来“大体正常”，最容易漏。
2. **Network 零外链**(Network 面板，刷新一次)。这是宿主“单文件复制到 %TEMP%”机制的生死线：任何外链字体/图片/样式在真机直接断链。浏览器环境宽松，外链照样渲染，**只有 Network 面板能暴露它**。
3. **窄窗比例测试**(Device toolbar 设 220×810,模拟悬浮窗)。看三件事：fit 按高缩放、贴右不溢出不裁切；44px 的百分比缩到 0.4 倍后还清不清楚；月牙空隙在白底下轮廓是否干净。你在 OpenDesign 确认的是大尺寸效果，窄窗才是真机的世界。
4. **演示数据回落正常**。四环显示写死的 73%/21%/52%/0/5——这证明数据桥的“浏览器回落分支”没被合入搞坏。
5. **手动喂一次假数据，验数据桥渲染端**。Console 里直接调：
   ```js
   butlerApply({account:{fiveHour:{pct:15},weekly:{pct:25},mcpMonthly:{pct:35}},keys:[]})
   ```
   四环应该立刻变成 15/25/35、key 环变"—"。这个函数在浏览器里也能调(它在 `chrome.webview` 守卫**外面**)，一条命令就能验完整个数据渲染路径，不用真机等宿主推数据。
6. **锚点完整性**(Console 快查)：`document.getElementById('panelPath')`、`querySelector('.stage')`、`getElementById('arcPath')`、`querySelector('.fab-zone')` 四个都不返回 null。这是形状上报桥的全部依赖，缺一个真机的点击穿透掩码就错位，而浏览器里桥休眠、肉眼完全无感。
7. **resize 跟随**：拖动浏览器窗口边缘，面板应该实时贴右缩放不跳变(fit() 挂了 resize 监听)。

一句话：动画和视觉在第一次已经看完了，第二次的核心是**三条契约**——无报错、无外链、桥的锚点齐全——外加窄窗尺度这一项 OpenDesign 给不了的真实视角。



### butler-shot.ps1 截图干啥?

我先把这个脚本的实际内容读出来，再回答它存在的意义。

读完脚本了，它做的事很朴素：把悬浮窗**按物理像素 1:1 从屏幕上抠下来存成 PNG 文件**。具体三步：先用 `SetProcessDpiAwarenessContext(-4)` 声明 Per-Monitor-V2 DPI 感知(否则 1.75 倍缩放下 `GetWindowRect` 返回的是被虚拟化的假坐标)，再按窗口类名 `ButlerWidgetWnd` 枚举找到悬浮窗，最后 `CopyFromScreen` 把那个矩形区域原样拷到 `%TEMP%\butler-shot.png`。

**它存在的理由不是“给你看”，而是三个“肉眼看屏幕”做不到的事：**

1. **给 AI 当眼睛——这是最核心的一条。** 你让我(或任何 zcode 会话)改完 UI 验证效果时，我看不见你的桌面，但我能读 PNG 文件。截图把“悬浮窗此刻的真实渲染状态”变成一个 AI 可读的证据文件，整个验证闭环才成立：改代码 → ctl 重启 → 读日志 → 读截图 → 判断是否通过。SOP 把每步都设计成命令级，就是因为每一步的产物(日志、PNG)都要能被 AI 消费——你自己在屏幕上看到“对了”这件事，传不进会话里。

2. **物理像素级的边缘质检。** 悬浮窗只有约 112×1050 物理像素，屏幕上肉眼判断“大体对”没问题，但这个项目真正容易翻车的都是 1–2px 级的合成问题：透明月牙空隙和面板黑边之间有没有一条白色/亮灰过渡带(合成没配对的典型症状)、掩码边缘贴不贴曲线、DPI 换算差一个像素。SOP 里那段像素剖面模板就是干这个的——沿扫描线逐像素读 RGB,期望“桌面色直接进面板色，中间不得出现 255 白或亮灰带”。这种判定在截图上放大看是确凿的测量，在屏幕上是猜。

3. **留档回归。** PNG 是文件，能跨迭代对比：改前一张、改后一张，或者按版本存档。屏幕状态转瞬即逝，你说“好像跟上次不一样”时没有证据可查。

另外有个细节：它用的是 `CopyFromScreen` 屏幕抓取而不是窗口自绘捕获，所以透明空隙里拍到的是**你桌面当时的真实内容**——这恰好也是对“透明合成真的生效了”的一次验证(如果 WebView2 透明失败，空隙会是白底而不是你的壁纸)。

什么时候可以不用它：你本人改了个颜色、就想扫一眼对不对，直接看屏幕完全够。什么时候必须用：让 AI 执行“改完并验证”的闭环、动了几何/掩码/合成相关代码、或需要和上一版对比时——前两条没有截图就没有证据。



### 如果我已经有了一个能正常运行的基础版带桥的项目UI,我在这个基础上拓展UI,是带桥给OpenDesign增加UI比较好还是不带桥的比较好

直接给结论：**不带桥，但不是退回卡片式旧原型，而是“正本剥桥”的设计基线**。理由和边界如下：

#### **为什么不带桥**

1. **OpenDesign 是生成式设计工具，不守桥。** 你的流程本身就是“OpenDesign 产出原型 html → 交给 zcode 合入”——它每次输出的是新生成的文件。70 多行 `chrome.webview` 守卫里的桥代码对设计工具来说是它不理解的异物，大概率被重写丢弃，或者更糟——被“好心修改”(比如改了它以为没用的 `panelPath` 常量)。给了也是白给，还引入“看起来带桥、锚点全错”的最阴险失效模式。
2. **桥在设计环境里本来就零作用。** 整段桥包在 `if (window.chrome && window.chrome.webview)` 里，OpenDesign 预览、浏览器里全休眠。设计阶段它不提供任何视觉信息，纯粹是噪音。
3. **桥的正确性看锚点，不看它是否出现在设计稿里。** 桥能不能工作，取决于 `#panelPath`、`.stage`、430×2025、fab 那 组常量在最终文件里对不对——这些由**合入的人(你+zcode)**保证就行，不需要桥本身陪跑设计全程。

#### **但“不带桥”有一个不能丢的东西：widget 模式的视觉骨架**

给 OpenDesign 的基线必须保留这些，否则新 UI 生在错误的上下文里，合入后位置/缩放全错：

- 430×2025 舞台、**贴右布局**、透明背景的月牙空隙(新元素得知道“左边是透的，只有右侧 ~211px 是面板”)
- `:root` 里的颜色 token
- 关键锚点结构:`#panelPath`、`.stage`、`#arcPath`、`.fab-zone`、四个环的 ID——新 UI 绕开它们设计，桥就不用动

也就是做一个 `设计基线.html`(正本剥掉 `<script>` 里的桥段、保留视觉骨架)，每次拓展 UI 都以它为 OpenDesign 的起点，产出再合回正本。方向永远是：**桥留在正本不动，视觉从无桥侧流向正本**。

#### **一个更重要的认知：拓展 UI 必然要拓展桥，这是代码活**

新增 UI 面板不只是加视觉——桥必须跟着长：

- **新可见形状要进 shape 上报**，否则宿主掩码不认它，点击直接穿透到桌面；
- **新可交互区要加拖动排除**(现在拖动桥只排除了 `.fab-zone`——如果你加了个设置面板，点面板上的按钮会变成**拖整个窗口**，因为 `pointerdown` 全被 drag 桥吃掉)。

这两件事需要理解宿主协议才能改对，是 zcode 在正本里干的活，指望 OpenDesign 顺手做对不现实。这也是“桥归正本、视觉归设计工具”这条分工的自然推论。

#### **长期解法**

如果不想每次都维护“设计基线+合入”这道工序，值得花一次功夫做之前提过的改造：把桥里的硬编码锚点(317/1675、84、22.3 这些)改成运行时从元素实测，桥变几何无关。到那时你就可以直接把**带桥正本**丢给任何工具改视觉，改完原样跑，“带不带桥”这个问题就不存在了。要做的话告诉我，改动集中在 487–524 行那一段。
